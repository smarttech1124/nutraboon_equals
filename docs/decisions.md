# Nutraboom Equals MVP — Architecture Decision Record

This document records decisions that should not be silently changed during implementation.

## ADR-001 — Modular Monolith

**Decision:** Build the MVP as a modular monolith.
**Reason:** The product is early-stage and has a small number of domains. A modular monolith provides clear boundaries without microservice deployment complexity.
**Consequence:** Modules must have clear responsibilities even though they live in one application.

## ADR-002 — Text First, Voice Second

**Decision:** Text chat is the primary MVP interaction. Voice is designed as an extension.
**Reason:** The conversational nutrition workflow needs to be validated before investing in speech infrastructure.
**Consequence:** The chat API must accept text independently from the UI implementation.

## ADR-003 — Single Home Page

**Decision:** The MVP has one primary public page. The chatbot is launched from that page.
**Reason:** The initial product objective is to validate conversational nutrition assistance rather than navigation complexity.
**Consequence:** Avoid multi-page marketing architecture during MVP.

## ADR-004 — Conversational Elicitation

**Decision:** The AI asks one useful follow-up question at a time.
**Reason:** Users should feel like they are talking to an assistant rather than completing a form.
**Consequence:** Conversation state must track known and missing information.

## ADR-005 — Deterministic Calculations

**Decision:** Financial and nutrition calculations should be performed by application code.
**Reason:** LLMs can make arithmetic mistakes.
**Consequence:** The AI explains calculated results but does not own the calculations.

## ADR-006 — Nutrition Data Has Provenance

**Decision:** Nutrition records must identify their source.
**Reason:** Nutrition information should not be silently generated by an LLM.
**Consequence:** Seed/database records should contain source metadata.

## ADR-007 — Price Data Is an Estimate

**Decision:** MVP price information is explicitly treated as estimated unless connected to a verified live source.
**Reason:** Food prices vary by location, retailer, season, and time.
**Consequence:** The UI must not imply that static prices are guaranteed current prices.

## ADR-008 — Nigerian-First Food Data

**Decision:** The initial dataset prioritizes foods commonly consumed in Nigeria.
**Reason:** The product should be locally useful rather than relying only on generic Western food examples.
**Consequence:** Food aliases and local terminology should be supported (e.g. `garri / gari`, `pawpaw / papaya`). Aliases should be data-driven rather than hard-coded throughout the application.

## ADR-009 — Allergy Validation Outside the LLM

**Decision:** Declared allergies must be enforced by application logic.
**Reason:** Safety-critical exclusions should not depend entirely on probabilistic model behavior.
**Consequence:** Meal plans undergo deterministic validation before presentation.

## ADR-010 — No Medical Diagnosis

**Decision:** The product provides general nutrition information and meal-planning assistance, not medical diagnosis or treatment.
**Reason:** The MVP is not a clinical product.
**Consequence:** Medical and high-risk nutrition scenarios require conservative responses and appropriate professional-care guidance.

## ADR-011 — No Authentication in MVP

**Decision:** Users do not need an account for the initial experience.
**Reason:** Reducing signup friction allows the product's core conversational experience to be tested.
**Consequence:** Conversation state can initially be session-based. Permanent history can be added later.

## ADR-012 — Server-Side AI Credentials

**Decision:** AI credentials must never be exposed to the browser.
**Reason:** API secrets must remain server-side.
**Consequence:** All model calls go through server-side application code.

## ADR-013 — Provider Abstraction

**Decision:** AI calls should go through an internal provider interface.

```ts
interface AIProvider {
  generateResponse(request: AIRequest): Promise<AIResponse>;
}
```

**Reason:** This prevents application logic from becoming tightly coupled to one model provider.
**Consequence:** The MVP may use one provider, but provider-specific code stays isolated.

## ADR-014 — Structured AI Responses

**Decision:** AI outputs should use structured schemas wherever possible.
**Reason:** The application needs reliable access to intent, meals, budget information, and safety metadata.
**Consequence:** Natural-language responses are still displayed to users, but the backend should work with structured data.

## ADR-015 — Progressive Context Collection

**Decision:** The assistant collects only the information necessary to answer the current request.
**Reason:** Long questionnaires reduce conversational quality.
**Consequence:** The conversation orchestrator tracks known facts, missing facts, and current intent.

## ADR-016 — No Microservices

**Decision:** Do not create separate nutrition, AI, budget, and meal-planning services at deployment level.
**Reason:** The MVP does not justify distributed-system complexity.
**Consequence:** Use internal modules with strong interfaces.

## ADR-017 — Safety Before Presentation

**Decision:** Generated meal recommendations pass through validation before being shown.
**Reason:** Safety requirements should be enforced independently of the model.
**Consequence:** The system may reject or modify a generated plan before returning it.

## ADR-018 — LOOP Engineering

**Decision:** Development follows Locate → Outline → Operate → Prove → Document → Repeat.
**Reason:** AI-assisted development can introduce large speculative changes. LOOP keeps implementation incremental and verifiable.
**Consequence:** Claude should not attempt to build the entire product in one uncontrolled generation cycle.

## Implementation decisions (Phase 1, 2026-10-01)

## ADR-019 — Next.js App Router + TypeScript

**Decision:** Use Next.js 16 (App Router) with TypeScript, Tailwind CSS 4 and npm.
**Reason:** One deployable app serves the home page and `/api/chat` route handlers, which fits ADR-001 and ADR-012.
**Consequence:** Server-only code (AI providers, secrets) lives under `lib/` and is imported only from route handlers.

## ADR-020 — Google Gemini as Default Provider, Switchable by Config

**Decision:** The first real `AIProvider` implementation is Google Gemini (`@google/genai`). The active provider is chosen by the `AI_PROVIDER` environment variable (`gemini` | `mock`).
**Reason:** Product owner choice. Switching must not require application changes (ADR-013).
**Consequence:** Adding a provider (e.g. Anthropic, OpenAI) means adding one file in `lib/ai/` and one case in `lib/ai/index.ts`. A deterministic `mock` provider exists for tests and for local development without a key.

## ADR-021 — PostgreSQL + Prisma

**Decision:** Persistent data (foods, prices, meals) uses PostgreSQL via Prisma migrations, starting in Phase 2.
**Reason:** Product owner choice. It matches architecture.md and gives reproducible migrations and parameterized queries (CLAUDE.md §26, §29).
**Consequence:** Phase 1 has no database. Conversation state is held in memory until there is a defined privacy/retention requirement (CLAUDE.md §28).

## ADR-022 — Nutrition Data Sources

**Decision:** Seed nutrition values come from the FAO/INFOODS West African Food Composition Table (2019) for West African foods, and USDA FoodData Central for foods it does not cover.
**Reason:** Both are published, citable sources. The FAO table covers Nigerian staples (garri, yam, plantain, etc.).
**Consequence:** Every record stores `source`, `source_url`, `source_version` and `retrieved_at`. Values are never written from memory (ADR-006).

## ADR-023 — In-Memory Conversation Store and Rate Limiter (Phase 1)

**Decision:** Conversation state and rate-limit counters live in process memory, with a TTL and size caps.
**Reason:** This is the smallest slice that supports multi-turn chat without storing raw conversations durably.
**Consequence:** State is lost on restart and is not shared across instances. Both must move to a shared store (Postgres or Redis) before running more than one server instance.

## ADR-024 — Vitest + Testing Library

**Decision:** Unit, integration (route handler), UI and safety tests use Vitest, with jsdom and React Testing Library for components.
**Reason:** Fast, TypeScript-native, and one runner for every test category.
**Consequence:** Tests never call a real AI provider. They use the mock provider or an injected fake.

## Implementation decisions (Phase 2, 2026-10-01)

## ADR-025 — Generated Seed File with Source Checksums

**Decision:** `prisma/seed/foods.json` is generated by `scripts/food-data/build_food_seed.py` from the official WAFCT 2019 workbook and USDA SR Legacy CSVs, plus a hand-curated `catalog.json` that holds no numbers.
**Reason:** It keeps ADR-006 and ADR-022 checkable: every value can be traced to a source row, and the source files' SHA-256 hashes are recorded.
**Consequence:** Nutrient values are changed only by rebuilding from source. The seed command makes the database match the file exactly (deterministic, re-runnable).

## ADR-026 — Nutrients from WAFCT, Serving Weights from USDA

**Decision:** Nutrient values per 100 g come from WAFCT 2019. Household serving weights (e.g. "1 medium orange = 131 g") come from USDA SR Legacy `food_portion`. Per-serving values are calculated by `scaleNutrients` (ADR-005).
**Reason:** WAFCT has no household measures. USDA portion weights are documented and citable.
**Consequence:** Each food records both sources. Foods with no matching USDA portion have no serving and are described per 100 g.

## ADR-027 — Data-Driven Alias Matching

**Decision:** Foods are found in messages by whole-word, longest-phrase matching against a `FoodAlias` table. Aliases are normalised (lowercase, no accents or punctuation) and must be unique across foods. At most 3 foods are matched per message.
**Reason:** This is deterministic and testable, and supports local names (garri/gari, pawpaw/papaya) without code changes (ADR-008).
**Consequence:** Matching does not resolve pronouns ("compare it with banana") or misspellings. The model receives verified data only for foods named in the current message.

## ADR-028 — Food Data Is Optional at Runtime

**Decision:** If the database is not configured or a lookup fails, the chat turn continues with no verified data. The failure is logged as `degraded: ["nutrition_unavailable"]`.
**Reason:** The prompt already forbids quoting figures without verified data, so degrading is safe, and it is better than failing the whole reply.
**Consequence:** Monitor `degraded` in logs. A database outage reduces answer quality but not availability.

## ADR-029 — Allergen Tags on Foods

**Decision:** Each food carries allergen tags (`peanut`, `egg`, `milk`, `fish`, `crustacean`, `soy`, `wheat`), set from what the food is.
**Reason:** Phase 5 allergy filtering (ADR-009) needs deterministic allergen data. Tagging now avoids a later backfill.
**Consequence:** Tags are curated in `catalog.json`. Refined oils are tagged conservatively (groundnut oil → `peanut`).

## ADR-030 — Retry Transient AI Provider Errors

**Decision (2026-10-01):** The Gemini provider retries HTTP 500/502/503/504 up to twice with backoff (about 0.5 s, then 1.5 s, plus jitter). Each attempt has a 20 s timeout. Other errors are not retried: bad key, missing model, invalid request, and 429 (quota or rate limit), because retrying a 429 only uses up more quota. The default model is `gemini-3.8-flash`, because Google closed `gemini-2.5-flash` to new users.
**Reason:** Overload (503) is common and usually short-lived. One blip should not fail a user's message.
**Consequence:** In the worst case a failed turn takes about 3 attempts × 20 s before the user sees the error. `withRetry` in `lib/ai/retry.ts` is provider-neutral, so future providers can reuse it.

## Implementation decisions (allergy check brought forward from Phase 5, 2026-10-01)

## ADR-031 — Deterministic Allergy Enforcement

**Decision:** Declared allergies are detected in user messages by code (`detectDeclaredAllergies`), stored in conversation state for the rest of the conversation, and sent to the model as a hard-exclusion context layer. Every reply is checked by `validateReply`: each entry in the model's structured `recommendedFoods` is checked strictly, and each message sentence is checked unless it clearly excludes the allergen ("left out", "instead of", "without", "allergy" …). A failing reply is regenerated once with a correction. If it fails again, the app returns a fixed safe message.
**Reason:** ADR-009 and ADR-017. Live testing showed Gemini suggesting groundnut oil after a declared peanut allergy.
**Consequence:**

- The app writes a visible 🛡️ notice: it names conflicting foods the user mentioned ("groundnut oil contains peanut"), or states the exclusion when the reply suggests foods.
- Logs record violation counts, whether the reply was regenerated, and whether the fallback was used. They never record allergen or food names.
- Known limits: dishes whose recipes vary (moi moi, egusi soup) are not assumed to contain egg or crayfish; an allergy cannot be withdrawn later in the same conversation; detection needs an allergy cue word ("allergic", "can't eat", "avoid", …).

## ADR-032 — Allergen Vocabulary in Code

**Decision:** Allergen terms, including Nigerian names and products (groundnut, epa, kuli kuli, suya/yaji, ede, semovita …), live in `lib/safety/allergens.ts`, not in the database. Longest-phrase matching plus explicit overrides handle false friends ("garden egg", "coconut milk", "tiger nut").
**Reason:** Allergy safety must keep working when the database is down (ADR-028).
**Consequence:** A test checks that every alias of every allergen-tagged food in `foods.json` is caught by the vocabulary, so the two cannot drift apart silently.

## Implementation decisions (Phase 3, 2026-10-01)

## ADR-033 — Product Renamed to Nutraboom Equals

**Decision:** The product name is **Nutraboom Equals** (previously NutriChat) in the UI, the assistant's prompt, docs and the npm package name (`nutraboom-equals`).
**Reason:** Product owner decision.
**Consequence:** Infrastructure names are unchanged to avoid breaking existing setups: the project folder, the local database name (`nutrichat`) and the dev-server config name. Earlier ADRs keep their original wording.

## ADR-034 — Conversation Profile from Structured Model Updates

**Decision:** Each reply may include a structured `profileUpdate` (household, ages, pregnancy, allergies or "none", foods to avoid, food at home, budget, plan length). The app validates it, merges it into `Conversation.profile`, and feeds it back as "Known facts (never ask for these again)". The app, not the model, computes what a meal plan still needs, in the CLAUDE.md order: who → ages → allergies → food at home.
**Reason:** It implements CLAUDE.md §20 and ADR-004/015. Understanding free text is the model's job (§11); state and rules are the app's.
**Consequence:** A malformed `profileUpdate` is dropped, not fatal. Allergies the model reports are mapped through the allergen vocabulary and enforced like detected ones. "No allergies" is also detected in code. Profile data lives only in the in-memory conversation store (ADR-023) and is never logged.

## ADR-035 — AI-Composed Meal Plans, Validated by the App

**Decision:** The model composes meal plans (CLAUDE.md §11) as a structured `mealPlan` (days → meals → foods, optional portion notes and notes). The app validates its shape and checks every dish name and food against declared allergies, foods to avoid, and child-feeding rules (no honey under 12 months; no whole nuts, groundnuts or popcorn under 5). A failing or malformed plan is regenerated once, then replaced by a safe fallback. The UI shows the plan as a card with a fixed "needs vary" note.
**Reason:** ADR-017 (safety before presentation) and project_requirements §6.
**Consequence:** There is no Meal table yet. Nothing would read it until Phase 4 costs plans against prices. When it is added, plans can be grounded in curated dishes, and the checks stay the same.

## Implementation decisions (Phase 4, 2026-10-02)

## ADR-030 (amended) — Retrying Rate Limits

**Decision:** A 429 is retried **once**, and only when the provider's error asks for a wait of 5 seconds or less (Google's `retryDelay`). The provider waits for at least that long. Any other 429 is not retried.
**Reason:** Free-tier keys have per-minute limits that clear in seconds. Live testing also showed the same short `retryDelay` on an exhausted daily quota, so more than one retry would only waste requests.
**Consequence:** A user briefly over the per-minute limit usually still gets an answer, a few seconds later.

## ADR-036 — Price Estimates from NBS, Only with a Documented Unit

**Decision:** Price estimates come from the NBS _Selected Food Price Watch_ (May 2026): national averages plus averages for the six geopolitical zones. They are stored in `PriceItem`, `PriceItemAlias` and `PriceEstimate`, loaded from a generated `prisma/seed/prices.json`. An item is included only when NBS documents its unit, in the item label or the report text. The user's state or major city is mapped to its zone; otherwise the national average is used.
**Reason:** CLAUDE.md §14 and §25 (never fabricate prices) and ADR-007. NBS is official and covers every state. WFP's dataset was rejected because its recent retail prices cover only three north-eastern states (see `docs/price-data.md`).
**Consequence:**

- 17 items are priced now.
- Rice, plantain, meat, fish and others are listed as "no price estimate" until their NBS units are confirmed.
- Estimates are always labelled with month, region and source, and shown to the nearest ₦10.
- NBS publishes no per-state averages in the workbook, so zone is the finest level.

## ADR-037 — Budget Planning: the Model Proposes, the App Prices

**Decision:** For budgets, the model returns a structured `shoppingList` (item and quantity in the price unit) and `fromHome`. The app prices it, totals it and works out what is left (`lib/budget`), and returns the result as `metadata.budget`. Two checks run on every reply alongside the safety checks:

1. Any naira amount in the message that is not the user's budget or a provided estimate is rejected.
2. A shopping list whose shown total exceeds the budget is regenerated.

The shown total is the sum of the shown (rounded) lines, so the card always adds up.
**Reason:** CLAUDE.md §12 (no LLM arithmetic), §25 (never fabricate prices) and Journey C.
**Consequence:** Budget facts are gathered in Journey C order: food at home → people → one meal or the whole day. Budgets and locations stated by the user are detected in code and override the model's reading. Unpriced items are listed separately and left out of the total. If the price data is unavailable, the chat still answers but shows no costs (logged as `prices_unavailable`).

## ADR-038 — Vercel Deployment with Migrations at Build Time (2026-10-02)

**Decision:** `vercel.json` runs `scripts/vercel-build.mjs`. Production deployments run `prisma migrate deploy` and the idempotent seed before `next build`. Preview deployments skip the database unless `RUN_DB_MIGRATIONS=true`. Builds without a database URL skip it with a warning. Migrations and the seed use `DIRECT_DATABASE_URL` when set; the app uses `DATABASE_URL`. The chat route sets `maxDuration = 60`.
**Reason:** CLAUDE.md §26 (migrations, reproducible schema). Previews often share production environment variables, so migrating by default from previews is unsafe. Serverless Postgres usually needs a direct connection for migrations.
**Consequence:**

- A failed migration fails the deploy.
- Seed data changes ship with the code.
- ADR-023's in-memory conversation store and rate limiter are **not** reliable on Vercel's multi-instance runtime and must move to a shared store before real users.

## ADR-039 — Conversation State in PostgreSQL (supersedes ADR-023 for conversations, 2026-10-02)

**Decision:** Conversations (messages, intent, declared allergies, known facts) are stored in a `Conversation` table through `PrismaConversationStore` whenever `DATABASE_URL` is set. The in-memory store remains only for tests and local runs without a database. The store interface is async.
**Reason:** On Vercel, consecutive messages can reach different instances. With in-memory state, a declared allergy or household could silently disappear mid-conversation (ADR-038).
**Consequence:**

- **Retention:** each save sets `expiresAt` 2 hours ahead. Expired rows are treated as missing and deleted (at most one sweep a minute per instance, using an index on `expiresAt`), so raw conversations are not kept indefinitely (CLAUDE.md §28).
- **Failure is fatal for the turn:** if the store cannot load or save, the turn fails with the standard "trouble connecting" message (503, logged as `store_unavailable`). It never continues without saved facts such as allergies. The user's message is not persisted on failure, so retrying is clean.
- **Validation:** stored rows are validated on read; an unreadable row fails like an outage instead of being trusted.
- **Concurrency:** two messages sent at the same moment in one conversation resolve as last write wins. This is acceptable for one person chatting.
- **Rate limiting** is still in-memory per instance (ADR-023) and needs a shared store before public launch.
- **Related fix:** nutrition facts for foods containing a declared allergen are no longer sent to the model. "Allergic to peanuts" had been pulling in groundnut data, which led to blocked replies.

## ADR-040 — Rate Limiting in PostgreSQL (supersedes the rest of ADR-023, 2026-10-02)

**Decision:** When `DATABASE_URL` is set, the chat rate limit (20 messages per minute per client) is enforced by `PostgresRateLimiter` against a `RateLimit` table. Each check is one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING count` on clock-aligned one-minute windows. The in-memory limiter remains for tests and local runs without a database, and also uses aligned windows.
**Reason:** On Vercel each instance had its own counter, so the limit could be exceeded many times over. Clock-aligned windows make a single atomic statement possible, so concurrent requests on different instances are counted exactly (verified: 30 simultaneous requests across two instances → exactly 20 allowed).
**Consequence:**

- **Privacy:** the table stores an HMAC-SHA256 of the client address keyed with `RATE_LIMIT_SECRET`, never the address. Set the secret in production so the hashes cannot be reversed by trying every IPv4 address. Rows expire with their window and are swept at most once a minute per instance.
- **Fails open:** if the database is unavailable, requests are allowed and logged as `degraded: ["rate_limit_unavailable"]`. Rate limiting protects capacity, not safety; compare ADR-039, where the conversation store fails closed.
- **Burst at the boundary:** a client can send up to 20 messages at the end of one window and 20 more at the start of the next. That is acceptable for this purpose.
- **Shared addresses:** the client address comes from `x-forwarded-for`, which Vercel sets. Users behind one shared address (e.g. a mobile carrier) share a limit.

## Implementation decisions (Phase 5, 2026-10-02)

## ADR-041 — Medical Safety Layer in Code

**Decision:** Safety-sensitive situations are detected in code, and replies are checked in code, in addition to the prompt policy.

- **Detection** (`lib/safety/context.ts`): pregnancy (only from statements such as "I'm pregnant" or "20 weeks pregnant"; "not pregnant" wins; trimester from words or weeks), breastfeeding, medical conditions (diabetes, high blood pressure, kidney disease, sickle cell, heart disease, eating disorders, malnutrition, ulcer, gout, cancer, including Nigerian phrasing such as "sugar patient" and "genotype SS"), medication mentions (including _agbo_), and emergency red flags.
- **Checks** (`lib/safety/medical-rules.ts`, applied with the allergy and child rules before any reply is shown):
  - no medication or supplement doses (an amount next to a medicine word);
  - no advice to start, stop or change medication, unless framed as "don't" or "ask your doctor first";
  - in pregnancy, no alcohol (including palm wine and local brews), liver, raw or unpasteurised milk (_nono_), raw or undercooked eggs, meat or fish, or high-mercury fish (after NHS "Foods to avoid in pregnancy");
  - no foods at all when everyone involved is under 6 months (WHO: breast milk or formula only).
- **Notices:** when red flags appear, the app adds its own urgent-care notice ("go to the nearest hospital… or call 112"), whatever the model writes. The first time each sensitive situation (pregnancy, breastfeeding, child, each condition, medication) appears, the app adds a matching referral if the model gave none, and records it in `profile.noticesShown`.

**Reason:** CLAUDE.md §6, §7 and §22, and ADR-010 and ADR-017. Live testing showed the model sometimes breaks these rules; for example, it suggested solid food for a 4-month-old, and the check caught it.
**Consequence:**

- A medication-related violation that survives regeneration falls back to "I can't advise on medicine doses or changes…".
- Condition detection counts mentions, which is conservative: a general question about diabetes also triggers the dietitian referral.
- The model's own safety notices are always passed through, even when they repeat. A repeated referral is a minor annoyance; suppressing one could hide a genuinely new concern.
- Rule lists are curated and narrow. New rules need a cited source.

## Implementation decisions (Phase 6, 2026-10-02)

## ADR-042 — Hardening Decisions

**Decision:**

- **Database tests:** they run against a separate `<db>_test` database derived from `DATABASE_URL` (`npm run test:db`).
- **Accessibility:** axe-core checks run in the test suite. The chat dialog makes the rest of the page `inert` while open, and returns focus to the launcher only after the page is interactive again. The chat panel's header is a `div`, so it is not a second page banner.
- **Client timeout:** the client gives up after 70 seconds (just over the server's 60-second `maxDuration`) and shows a retry. It detects offline devices before sending.
- **Error pages:** friendly `error.tsx` and `not-found.tsx` pages; error details are never shown.
- **Lazy loading:** the chat panel is not lazy-loaded.

**Reason:**

- The database integration tests had never run, and live checks found a modal-focus bug that jsdom cannot detect.
- A hung request left users on the typing indicator forever.
- The home page's JavaScript is mostly the React and Next.js runtime, so lazy-loading the panel would save only a few KB for added complexity.

**Consequence:**

- Coverage tooling (`@vitest/coverage-v8`) and `axe-core` are dev dependencies only.
- Colour contrast, `<title>` and `lang` are checked in a real browser, not jsdom.
- Real mobile-network performance (e.g. Lighthouse on a throttled connection against the deployed site) is still to be measured once the app is deployed.

## Implementation decisions (Phase 7, 2026-10-03)

## ADR-043 — Voice Foundation with the Browser's Web Speech API

**Decision:** Voice input and read-aloud use the browser's built-in Web Speech API (`lib/voice/browser.ts`), behind small `SpeechToText` / `TextToSpeech` interfaces (`lib/voice/types.ts`).

- **Pipeline:** the chat still receives only text: microphone → transcript → the existing `sendMessage` → `POST /api/chat` → reply → speech. There are no server changes and no separate voice engine (architecture.md §14).
- **Review before sending:** the transcript is placed in the message box for review, never sent automatically.
- **Read aloud:** replies are read aloud only when the question was spoken. The urgent-care notice is read first, then the reply, the allergy note and the referral. ₦ amounts are read as "naira", and bullets and emoji are dropped. A "Stop reading" button cancels speech, and closing the chat stops listening and speaking.
- **Language:** recognition and speech use `en-NG` where the browser has it, falling back to other English voices.
- **Unsupported browsers:** where speech recognition is unavailable (e.g. Firefox), the microphone button is not shown.

**Reason:** CLAUDE.md §17 and ADR-002 call for a voice foundation without expensive real-time voice infrastructure. The browser API costs nothing and needs no server work. Reviewing the transcript before sending means a misheard food, allergen or medicine is caught before it shapes advice.
**Consequence:**

- **Privacy:** in Chrome and Edge, speech recognition audio is processed by the browser vendor's service. The microphone button's tooltip and the listening status say so, and so does the README.
- **Coverage:** works in Chrome, Edge and Safari; Firefox users type.
- **Future:** a server-side transcription service (for example for Nigerian languages, or for consistent privacy terms) can implement `SpeechToText` and be passed to `useVoice` without changing the chat.
- **Testing:** recognition accuracy and Nigerian accents can only be judged by people trying it on real devices.

## ADR-044 — Optional Fallback Gemini Model (2026-10-03)

**Decision:** When `GEMINI_FALLBACK_MODEL` is set, a request whose primary model fails after its retries is sent once to the fallback model, which has its own retries. Fallback happens for errors another model may not share: 5xx overload or server errors, 429 (quotas are per model), 404 (model unavailable), and timeouts or network errors. It does not happen for 400, 401 or 403, which every model would hit. The fallback is skipped if the primary already took 35 seconds or more, keeping the request inside the route's 60-second `maxDuration`. Each switch is logged as `ai_fallback` with model names and status only.
**Reason:** `gemini-3.8-flash` was repeatedly overloaded or out of free-tier quota during testing and in local use. Users saw "trouble connecting" when a lighter model could have answered.
**Consequence:**

- Replies from the fallback model may be plainer, but every safety and budget check still applies, because the checks run on the reply, not on the model.
- With no `GEMINI_FALLBACK_MODEL`, behaviour is unchanged.
- `GeminiProvider` now takes an options object (`model`, `fallbackModel`).

## ADR-045 — Listen Button on Every Reply (2026-10-03)

**Decision:** Every assistant reply has a **Listen** button wherever the browser can speak. It uses the same browser voice and text formatting as ADR-043 (urgent notice first, ₦ as "naira"). It becomes **Stop** while that reply plays, and starting another reply replaces the current one. Each playback carries a token, so a cancelled reading's late "ended" event cannot reset the reply now playing. Replies to typed questions still never play by themselves.
**Reason:** Phase 7 only read replies to spoken questions. Users who type, or who want to hear a reply again, had no way to listen.
**Consequence:** There is no new service, cost or privacy change. Voice quality still depends on the device (often no Nigerian English voice); see ADR-046.

## ADR-046 — Server-Generated Voice (Proposed, not built)

**Status:** Proposed future implementation. Nothing in this ADR is built.

**Problem:** Browser voices vary by device, rarely include Nigerian English, and cannot speak Yoruba, Hausa or Igbo. A consistent, natural voice needs speech generated on the server.

**Proposed design:**

1. **Provider:** a server-side speech provider behind a new `SpeechProvider` interface, like `AIProvider`. The first candidate is a Gemini TTS model on the existing key (e.g. `gemini-3.8-flash-tts`, listed on the current key); alternatives are Google Cloud Text-to-Speech and ElevenLabs. Choose by listening tests for Nigerian English and food names (garri, egusi, ugu) before building.
2. **Endpoint:** `POST /api/speech` with `{ conversationId, replyId }`. It never accepts arbitrary text. The server looks up the reply in the stored conversation, so the endpoint cannot be used as a free speech service.
   - Today only reply text is stored. The stored assistant message must also keep the text to be spoken (notices included) or the notices themselves, so the urgent notice is still read first.
3. **Client:** a `ServerTextToSpeech` implementing the existing `TextToSpeech` interface. It calls the endpoint and plays the audio with an `<audio>` element, so the chat and the Listen button do not change. It falls back to the browser voice if the request fails. It is selected by a setting such as `TTS_PROVIDER=browser|server`.
4. **Audio format:** Gemini TTS typically returns raw PCM. Convert it to a compact, widely playable format (e.g. Opus or MP3) on the server, keeping clips small for mobile data.
5. **Caching:** cache audio per reply (hash of the spoken text and voice) for no longer than the conversation's 2-hour retention, so replaying costs nothing.
6. **Limits:** a separate rate limit for speech; a maximum text length per request; and the route's `maxDuration` sized for speech generation.
7. **Safety:** read exactly the text on screen with the urgent notice first, never a model-written summary. The existing `speechForReply` stays the single source of what is spoken.
8. **Privacy:** reply text, which may include health details, goes to the speech provider. Update the privacy notice and README before enabling this, and check the provider's data terms. A paid tier is required.

**Prerequisites:** the user-facing privacy notice (see project_status.md); a paid AI plan; a voice trial with real users comparing browser and server voices.

**Acceptance criteria (when built):**

- The same voice on every device.
- The urgent notice is read first.
- Only stored replies can be spoken.
- Replays are served from cache.
- The browser voice is used if the server fails.
- Tests cover lookup, caching, rate limiting and fallback.

**Rough size:** a few days, plus voice evaluation and audio-format work.

## ADR-047 — AI Provider Settings Page (2026-10-04)

**Decision:** An admin page at `/em/chat/settings` manages the AI provider credentials and models that chat uses. It supports **Google Gemini, OpenAI and DeepSeek**. When no saved configuration is active, chat uses the environment variables exactly as before (`AI_PROVIDER`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_FALLBACK_MODEL`).

**Design:**

1. **Lifecycle:** submitted → verified → encrypted and stored → available → activated. A key that fails verification is **never stored**; only a metadata audit event is kept. An unverified key cannot become active.
2. **Verification:** after a format check, one tiny generation request ("ping", 1–16 output tokens) goes to the provider. This checks the key, the model and the account's ability to generate (credit, billing). No user data is sent. Errors map to fixed messages (`invalid_key`, `model_unavailable`, `no_credit`, `rate_limited`, `rejected`, `unreachable`). Provider error bodies are never shown or logged, because some quote part of the key.
3. **Storage:** `AIProviderConfig` holds the key encrypted with **AES-256-GCM** under `AI_CREDENTIALS_KEY` (32 random bytes). The configuration id and provider are bound in as additional authenticated data, so a ciphertext copied to another row will not decrypt. A masked hint (e.g. `sk-••••••••9X2A`) is stored for display. An HMAC fingerprint (separate HKDF subkey) detects the same key and model being added twice. Keys are decrypted only to verify them or to build the chat provider.
4. **One active configuration:** the single-row table `AIActiveConfig` (`CHECK (id = 1)`) points at the active configuration. Switching is one serializable transaction: deactivate A, activate B, write both audit events.
5. **Runtime:** `getChatProvider()` reads the active configuration, caching it for 30 seconds per server instance. A change made on the same instance applies at once; other instances pick it up within 30 seconds. If the lookup or decryption fails, chat falls back to the environment settings and logs `ai_config_unavailable` (error name only).
6. **Lifecycle actions:** activate, deactivate, re-check, change model (verified against the stored key first) and delete key (revoke). Revoking wipes the ciphertext and keeps the row for the audit trail. A re-check that fails definitively (`invalid_key`, `model_unavailable`, `no_credit`) marks the key **failed** and deactivates it if active. A transient failure changes nothing.
7. **Audit:** `AIConfigAuditEvent` records key added, check passed or failed, activated, deactivated, revoked and model changed. Each event holds provider, model, masked hint, a reason code and the actor, and never the key.
8. **Providers:** OpenAI and DeepSeek share `OpenAICompatibleProvider` (Chat Completions over `fetch`, no new dependency). OpenAI gets the reply JSON schema as structured output (`strict: false`, since the schema has optional fields). DeepSeek has no schema mode, so it uses JSON mode with the schema in the system prompt. Every reply is still validated by `parseAssistantOutput` and passes all safety checks.

**Kept separate:** these are **system-owned AI provider credentials** only. Platform API keys (issued to outside apps) and third-party connector credentials (OAuth tokens) are different concepts, with different permissions and rotation. They are not built, and would get their own tables.

**Consequences:**

- Changing or losing `AI_CREDENTIALS_KEY` makes every stored key unreadable. Chat falls back to the environment settings and keys must be added again. There is no master-key rotation yet; it would need a re-encryption script.
- Saved configurations have one model each and no fallback model. `GEMINI_FALLBACK_MODEL` applies only to the environment settings.
- The safety layer is provider-independent, but it has only been tested live with Gemini. Run the safety prompts against any new provider before relying on it.
- `next dev` logs server-action arguments. The key reaches the action only inside `FormData`, which the log prints as `{}`.

## ADR-048 — Admin Sign-in for the AI Settings Page (Scope Change, 2026-10-04; replaced by ADR-060 and ADR-061)

**Decision:** The product owner approved a minimal admin area for the AI settings page only. This is an explicit exception to "Do NOT build: Authentication. Admin dashboards." in CLAUDE.md §1. Users still need no account (ADR-011 unchanged).

**Design:**

- **One shared admin password,** stored as an scrypt hash in `ADMIN_PASSWORD_HASH` (format `scrypt:N:r:p:salt:hash`, without `$`, because Next.js expands `$NAME` in `.env` files). Generate it with `npm run admin:secrets`.
- **Session:** an HMAC-signed cookie (`nbe_admin`: HttpOnly, SameSite=Strict, Secure in production, Path `/em`, 8 hours). It is signed with `ADMIN_SESSION_SECRET` together with the password hash, so changing the password signs every session out. The cookie holds only timestamps.
- **Brute-force limit:** 5 sign-in attempts per 15 minutes per client address, using the shared rate-limit table. Unlike chat, sign-in **fails closed** if the limiter is down.
- **Authorization:** every server action calls `requireAdmin()` itself, because actions can be called by direct POST. Next.js server actions also reject cross-origin requests (Origin vs Host), which covers CSRF.
- **Hidden when off:** the page returns 404 unless `ADMIN_PASSWORD_HASH` and `ADMIN_SESSION_SECRET` are set. It is marked `noindex` and rendered per request (never prerendered).

**Consequences:** there are no individual admin identities, so the audit actor is always "admin". The upgrade path is an admin-user table or an auth library, if more people need access or named audit entries.

## ADR-049 — Longer, More Reliable Voice Capture (2026-10-04)

**Decision:** Voice input listens continuously and decides itself when the user has finished, instead of stopping at the browser's first pause.

- Listening ends after **3.5 seconds of silence** following speech, when the user taps ■, or at **2 minutes**. If nothing is said in 10 seconds, "I didn't hear anything" is shown.
- Browsers end recognition sessions on their own (often after a pause or about a minute). These are restarted, up to 10 times, keeping what was already said.
- Words the browser has not yet confirmed are **kept**, not dropped, when a session ends. After the user taps ■, the browser has up to 3 seconds to deliver its last words before capture finishes anyway.
- The input shows three states: **Listening…** (with the live transcript), **Processing your last words…** (Send is disabled), and **Ready. Check the text, then press Send.** The transcript is still never sent automatically (ADR-043).

**Consequence:** long questions are no longer cut off. The microphone stays on through short thinking pauses, so users who are done can tap ■ to finish sooner.

## ADR-050 — Response Language Setting (2026-10-04)

**Decision:** A **Settings** screen in the chat (⚙) lets the user choose the reply language: Nigerian English (default), UK English, US English, **Yorùbá (Beta)** and **Igbo (Beta)**.

- **Storage:** there are no accounts (ADR-011), so the choice is saved in this browser's storage only (`nbe:settings`) and sent as `language` with every chat request. If storage is blocked, it applies for the visit. An unknown value falls back to Nigerian English instead of failing the request.
- **Prompt:** a language layer tells the model which language to write. For Yoruba and Igbo:
  - The model must also return `englishMessage` (the same reply in English). The safety checks read **both** texts: local names like "epa" (groundnut) appear in the translated text, English ones in the English text. A reply without `englishMessage` fails the checks and is regenerated.
  - Food lists (recommendedFoods, shoppingList, fromHome, plan foods) stay in English, so the allergy vocabulary can check them.
  - `safetyNotice` stays in English, and the app's own notices (urgent care, allergy, referral) are in English. Yoruba and Igbo are marked **Beta** in the settings, with that explanation, until a native speaker reviews prompts and notices.
- **Voice:** recognition and read-aloud use the chosen language (`en-NG`, `en-GB`, `en-US`, `yo-NG`, `ig-NG`). A reply is read aloud only if the device has a voice for that language: an English voice reading Yoruba would be unintelligible. Where the browser cannot recognise the language, the user is told to type.

**Consequences:** the outcome card's labels stay in English for now. Translation quality and safety wording in Yoruba and Igbo are unreviewed; see project_status.md.

## ADR-051 — Outcome Interface (2026-10-04)

**Decision:** "Don't just answer the user: produce a useful outcome." A reply that contains a result leads with an **outcome card**, and the model's text follows it as a short lead-in or follow-up question.

- **Meal or budget plan:**
  - the title, e.g. "Your ₦2,000 meal plan", with people and days ("For 3 people • 1 day");
  - the estimated total and what is left;
  - each meal with its **estimated cost to buy**;
  - the shopping list, the budget summary, and a nutrition focus.
- **Food question:** "Orange at a glance", or "A vs B" for a comparison, with per-serving energy, macronutrients and the nutrients the food stands out for.
- **Built by code, never by the model:**
  - The title, subtitle and costs come from validated data. Per-meal costs come from the model tagging each shopping item with `forMeal` (the dish name), matched to the plan ignoring word order. Prices still come only from NBS estimates (ADR-036, ADR-037).
  - **Nutrition focus** lists, for up to 4 nutrients, the suggested foods that are in the **top quarter of our own food data** (per 100 g) for that nutrient. This needs no outside reference values and never states a figure. Foods the user is allergic to are never listed. The foods used are credited as data sources.
  - Food facts are calculated from the verified per-serving data (ADR-027).
- **Prompt:** an outcome layer asks for structured fields and a short message. When the user has a budget, everything to buy must be in `shoppingList` with `forMeal`, so the card can cost it. This also applies when all the facts arrive in one message.
- **Voice:** reading a reply aloud gives the urgent notice first, then a summary of the card (title, meals with costs, total, what is left), then the text. The summary is read only for English replies, because the card is in English.

**Consequence:** `metadata.outcome` is added to the chat response. `mealPlan` and `budget` are unchanged.

## ADR-052 — XEELAA API Integration with Automatic Fallback (2026-10-04)

**Decision:** The admin settings page gets a **XEELAA API** section with a key field, a **Use XEELAA API** switch, its status, a re-check, usage figures and key deletion. When the switch is on and the key is verified, chat sends each turn to XEELAA first. **Any** failure answers with the existing provider instead (the active saved configuration or the environment settings), so the user never sees an error caused by XEELAA.

**Design:**

- **Storage:** a single-row `XeelaaIntegration` table (`CHECK (id = 1)`) holds the key encrypted with AES-256-GCM under `AI_CREDENTIALS_KEY` (as ADR-047), a masked hint, the switch, status and the last error code. Audit events use the ADR-047 trail with provider "xeelaa".
- **Verification:** XEELAA documents `GET /api/v2/verify`. Checked live on 2026-10-04, it answers 200 with or without a key: it reports the API's status and does not check keys. Keys are therefore checked with the authenticated `GET /api/v2/usage`, which answers 401 "Invalid or expired API key." for a bad key. If `/usage` fails for any other reason (server error, time-out after 20 seconds, unexpected status), `GET /api/v2/me` is tried before giving up. The admin message names the actual reason: rejected key, rate limit, time-out, XEELAA server error (with its HTTP status), or no connection. Each check logs `xeelaa_check` with the endpoint, status or error name and duration, never the key. (Added 2026-10-05 after a real key got the old catch-all message "Could not reach XEELAA".) In development, the cached settings services are rebuilt whenever `lib/ai/settings/runtime.ts` reloads; before that fix, hot reload kept running the old key check until the dev server restarted. A key is saved only after that check passes. The switch can only be turned on after a fresh check.
- **Chat:** `XeelaaProvider` sends one message to `POST /api/v2/ai/chat?search_web=false&reasoning=false`. The message holds the layered prompt, the conversation and the JSON reply contract. The reply text is taken from the `{ success, message, data }` envelope (or similar fields) and must pass `parseAssistantOutput` and every safety check like any provider. The request body format and the reply's field are **not documented and not yet confirmed** with a real key. If they differ, every XEELAA call falls back, and chat still works.
- **Fallback:** `FallbackProvider` tries XEELAA with a 15-second limit and no retries. On failure it logs `ai_primary_fallback` (category and HTTP status only), answers with the default provider, and skips XEELAA for 60 seconds.
  - A 401 or 403 in chat marks the key **invalid**. The admin page then shows "Key not working" with the reason, and chat stops trying XEELAA until a passing re-check.
  - Other failures (timeouts, 5xx, invalid output) only start the 60-second pause.
- **Switch-off:** turning XEELAA off, deleting its key, or a failed key takes effect at once on that server instance and within 30 seconds on others. Chat then uses the default provider; nothing else changes.

**Consequences:**

- Messages, including health details, go to XEELAA when it is on. Add XEELAA to the privacy notice and check its data terms before enabling it for real users.
- Run the safety prompts through XEELAA before relying on it. Its replies pass the same checks, but quality is untested.
- A XEELAA failure adds up to 15 seconds before the fallback answers (then 60 seconds of going straight to the fallback).

## ADR-055 — Conversation Behaviour From the Product Review (2026-10-06)

**Context:** the October 2026 product review asked for Equals to behave like a nutrition professional who listens: help first, ask one relevant thing, remember constraints, explain meals simply, no performative empathy. The product owner decided:

1. Keep **one question per reply** (CLAUDE.md §25).
2. **Allow medication literacy.**
3. **Keep reviewing the voice transcript before sending** (ADR-043).
4. Nutrients outside our data may be **named in general terms, using verified names only**.

**Decision:**

- **Prompt (conversation rules):**
  - no performative empathy, with the review's examples;
  - help first, then ask;
  - short replies by default (two to four sentences, more only for plans, safety, education or when asked);
  - when the parent describes a problem, the question is about that problem;
  - never ask about money unprompted;
  - ask children's ages before allergies;
  - leftovers first;
  - one family meal with adjusted textures;
  - reuse ingredients across days;
  - a plain "why" for every meal (shown in the card and read aloud), without figures.
- **Remembered constraints (profile):**
  - `unaffordableFoods`, enforced like avoided foods;
  - `cookingMinutes` and `hasFridge`;
  - `ingredientsNow`, which _replaces_ the kitchen list ("now I only have…"), where other ingredient updates add to it.
  - Refused foods continue to use `avoidFoods`.
- **Hints worked out in code** from the latest message, because prompt wording alone was not reliable in testing:
  - children mentioned without ages: ask their ages first;
  - an eating problem: ask about it;
  - leftovers: build around them.
  - A reply that suggests food but ignores the named leftovers is regenerated once.
- **Voice:** a spoken question sends `inputMode: "voice"`. The prompt then asks for at most three spoken-style sentences, with no lists.
- **Medication literacy:** the assistant may explain instructions the user already has. A sentence with a dose passes the dose check only if every dose in it is one the user stated. Advice to start, stop, change or compare a medicine is still blocked (ADR-041).
- **Nutrient claims:** `lib/nutrition/vocabulary.ts` lists verified nutrient names (FAO/INFOODS and WHO/FAO 2004 naming).
  - **Unknown names:** vitamin names not on the list ("vitamin B17") are blocked, unless the user raised the name, so the reply can debunk it.
  - **Figures:** every nutrient figure (kcal, kJ, mg, mcg, and grams of protein, fat, fibre or carbohydrate) must match this turn's VERIFIED DATA (within 10% for rounding), an earlier checked reply, or the user's own words. Portion weights ("500 g of rice") are not nutrition figures.
- **Resilience:** a reply in the wrong shape (`invalid_output`) is requested once more before the user sees "trouble connecting".

**Consequences:** each new check can cause one regeneration (a few seconds). The "why" lines are model-written, with no figures, and are checked like the message. Medication literacy relies on the user's own words being accurate; the reply always defers to the pharmacist or clinic when the user is unsure.

## ADR-057 — Spoken Confirmation of Voice Messages (2026-10-07)

**Context:** the review asked for a voice-first experience for blind and visually impaired parents. The product owner kept the rule that a transcript is reviewed before it is sent (ADR-043), because a misheard food or medicine could shape advice.

**Decision:** an optional setting, **"Read my voice message back, then let me say 'send'"** (off by default, saved on the device). When it is on, after a voice message:

1. Equals reads it back: "I heard: …. Say send to send it, or again to record it again."
2. It listens briefly for a reply (`COMMAND_LISTENING`: 1.2 s of silence ends it, 7 s maximum wait, no restarts).
3. Only a short, whole reply counts (`parseVoiceCommand`, four words at most):
   - "send", "yes" or "correct" sends the message;
   - "again" or "no" clears it and records again;
   - "cancel", silence or anything else leaves it unsent, with "Not sent. Check the text, then press Send."
4. Typing during the confirmation stops the listening. The message is still never sent without the user's say-so.

For everyone, the "Ready" status now includes the transcript in screen-reader text ("You said: '…'"), so screen-reader users hear what was understood without moving to the box. The spoken commands are English words, so confirmation works only when the reply language is an English variant. The settings screen says so for Yoruba and Igbo.

**Consequence:** this keeps review-before-send while letting a blind parent review by ear. It depends on the browser's speech recognition hearing "send" correctly; a misheard command at worst leaves the message unsent.

## ADR-061 — Accounts, Sessions and Admin Roles (2026-10-08)

**Context:** the specification introduces users, nutritionists, vendors, hospitals and administrators. The product owner chose in-house authentication. Chat stays usable without an account.

**Decision:**

- **Accounts:** `User` with an scrypt password hash (`lib/admin/password.ts`), at least 10 characters. Email is stored lowercased.
- **Sessions:** a random 32-byte token in an httpOnly cookie. Only its SHA-256 is stored (`Session`).
  - Main site: `nbe_session`, SameSite=Lax, 30 days, extended while used.
  - n-equals: `ne_admin_session`, SameSite=Strict, 8 hours, never extended.
  - Suspending an account, resetting its password or removing its last admin role ends its sessions.
- **Email links:** verification and password reset use one-time tokens (`AuthToken`, hashed, consumed atomically). Production sends no email until a provider is configured; reset then says it is unavailable.
- **Sign-in:** an unknown email and a wrong password get the same message, with equal work done. Attempts are rate-limited per client (sign-in 10 per 15 minutes, sign-up and reset 5 an hour), and the limit fails closed.
- **Admin roles:** super, platform, nutritionist, vendor, hospital, support and finance administrator. Role-to-permission mapping is code (`lib/auth/permissions.ts`); assigning roles is done in n-equals (Users & roles). Every page and server action checks its permission on the server. The last super administrator cannot lose that role, and nobody can suspend themselves. The first administrator is created with `npm run admin:create`.
- **Audit:** `AuditLog` records who did what to which record, with metadata only (never passwords, keys or message text). n-equals shows it under Audit log.

**Consequence:** organisations (`Organization`, `Membership`) exist in the schema for vendors and hospitals but have no screens yet.

## ADR-062 — Subscriptions, Entitlements and Platform Settings (2026-10-08)

**Context:** the specification forbids hard-coded limits: the free Meal Planner allows one or two days, paid plans more, all configurable in admin.

**Decision:**

- **Entitlements are data.** The registry (`lib/billing/entitlements.ts`) defines each entitlement with its type, range and free default: `mealPlanner.maxDays` (2), `mealPlanner.plansPerMonth` (4), `mealPlanner.shoppingList` (off).
- **Plans** (n-equals Plans) store a price in kobo, an interval (monthly or yearly), an audience and their entitlement values. A blank value falls back to the free tier.
- **`EntitlementService`** is the only place that answers what a subject may do. It merges the free tier (defaults plus the n-equals override) with every subscription that counts, and the most generous value wins:
  - an active subscription counts until its period end plus the grace days;
  - a past-due one counts until its grace date;
  - pending, canceled and expired ones never count.
- **Usage limits** are counted per Lagos calendar month in `UsageCounter`, with one atomic SQL statement, so two requests cannot both take the last use.
- **Platform settings** (`PlatformSetting`), edited under n-equals Settings, each with a schema and a default:
  - feature flags: Meal Planner, Paid plans, Nutritionists, Vendors, Hospitals, all off by default;
  - the free tier;
  - the grace period (3 days by default).
- **Manual grants** give a user a plan for a set number of days without payment, and never renew.

**Consequence:** the Meal Planner, nutritionist, vendor and hospital modules will read their limits and flags from this service when they are built. Nothing uses `mealPlanner.*` yet.

## ADR-063 — Paystack and Flutterwave Payments (2026-10-08)

**Context:** the product owner asked for both Paystack and Flutterwave.

**Decision:**

- **One interface** (`lib/payments/types.ts`) with two implementations. Both use the provider's own recurring billing: a plan created in their dashboard and named on our plan (a Paystack plan code, a Flutterwave payment plan id). Card details never reach this server.
- **Checkout** (account page, when "Paid plans" is on and the account email is confirmed):
  1. A pending `Subscription` is created with a random reference.
  2. The subscriber pays on the provider's hosted page.
  3. They come back to `/account/billing/return`.
- **Nothing is trusted from the browser or the webhook body alone.** Every payment is verified with the provider's API, and must match the plan's currency and be at least its price, before it grants or extends anything.
- **Webhooks** go to `POST /api/webhooks/{paystack|flutterwave}`:
  - Paystack: HMAC-SHA512 of the raw body with the secret key (`x-paystack-signature`).
  - Flutterwave: the dashboard secret hash in `verif-hash`, compared in constant time.
  - Body limit 64 KB. Each delivery is recorded in `PaymentEvent`, so a repeat is applied once, and each payment reference extends a subscription at most once. On failure the record is removed and the route answers 500, so the provider retries.
- **Events:**
  - a first payment activates the subscription;
  - a renewal moves the period on by one interval;
  - a failed renewal sets past due with the grace period;
  - cancellation keeps access to the end of the paid period.
- **Cancelling:** subscribers can stop renewal (Paystack `subscription/disable` with the email token; Flutterwave cancel after looking the subscription up by email and plan). Administrators can end a subscription at once; refunds are made in the provider's dashboard.

**Consequence:** this is tested with mocked provider responses only. Before switching "Paid plans" on:

- run real test-mode checkouts with both providers, including a renewal and a failed renewal;
- check that the webhook payloads match, especially Flutterwave renewal charges, which are matched by customer email and plan.

Only test-mode keys belong outside production.

## ADR-064 — Nutritionist Onboarding, Verification and Discovery (Phase B, 2026-10-08)

**Context:** the specification asks for nutritionist registration, AI-assisted qualification analysis, a marketplace with cards, matching from chat, and a nutritionist portal. The product owner decided:

- Users do not pay for sessions through Equals. Equals shows the session fee and the nutritionist's contact details; the nutritionist handles payment on their own terms.
- Qualification documents and photos are stored in Cloudinary.
- A directory listing is an entitlement.

**Decision:**

- **Onboarding** (`/nutritionist/join`, then the portal at `/nutritionist`): any signed-in account can start a `NutritionistProfile`. The portal has Dashboard, Profile, Qualifications, Availability, Appointments and Plan.
  - Before submitting, the profile needs a title, specialisations, state, session types, a fee, a contact method, weekly availability, at least one qualification and one document (`missingForSubmission`).
  - Statuses: draft → submitted → verified, or changes requested, rejected or suspended.
  - A verified profile goes back to review when its title, specialisations, experience, qualifications or documents change, and is hidden until approved again.
- **Files:** Cloudinary through signed REST calls (`lib/storage/cloudinary.ts`, no SDK).
  - Documents are uploaded as `private` and opened only through 5-minute signed links: by the owner (`/nutritionist/documents/[id]`) and by reviewers in n-equals, where each view is audited.
  - Photos are public under a random id and shown only once verified.
  - Files are checked by content (PDF, JPEG, PNG), up to 3 MB for documents and 2 MB for photos. Server-action bodies are limited to 4 MB, below Vercel's 4.5 MB cap. Uploads are rate-limited.
- **Qualification analysis** (`lib/nutritionists/analysis.ts`), advisory only:
  - Deterministic checks: degree listed, registration with a number, years given, claimed experience against the earliest qualification, expiry, documents.
  - An optional AI assessment through a new `generateJson` method on the providers, using the active saved configuration or the environment provider (never XEELAA). It returns relevance, support per specialisation, manual checks and a summary, validated with Zod; unclaimed specialisations are dropped.
  - The AI never sees documents, contact details or registration numbers. It is told it cannot verify credentials, and applicant text is passed as delimited data.
  - The analysis runs on submission, and a reviewer can run it again. The prompt version is stored with each result.
- **Review** (n-equals Nutritionists, `nutritionists.verify`): approve, request changes, reject, suspend or reinstate, with a note required for negative decisions. Nobody can review their own profile. Each decision is audited and notified.
- **Listing:** the Nutritionists feature flag is on, the account is active, the profile is verified, and the `nutritionist.listing` entitlement is held. That entitlement is off in the free tier by default and is given by a nutritionist plan or a grant.
- **Matching** (`lib/nutritionists/matching.ts`) is deterministic: availability, session type and fee filters; in-person-only nutritionists only nearby; then specialisation match, same state or zone, online, and fee. The AI never chooses who is shown.
- **Chat:** when a new sensitive situation gets a referral (pregnancy, child, a condition), or the user asks for a nutritionist or dietitian, the app adds up to three cards to the reply. It never does so in an emergency. A directory failure never breaks chat.
- **Directory and booking:**
  - `/nutritionists` and `/nutritionists/[id]` show the card details from the specification. Ratings are not built yet.
  - Contact details are shown to signed-in users.
  - Booking: a session request has a type, a time in Lagos time inside the nutritionist's hours (at least 2 hours ahead, within 60 days) and an optional note. The client consents to share their name, email and note. Requests are rate-limited and capped at 3 open per nutritionist.
  - The nutritionist accepts (overlaps blocked), declines, cancels or completes with a note for the client.
- **Notifications:** an in-app `Notification`, plus email when a provider is configured. The text is fixed and never contains health details.

**Consequence:** nutritionists see only what clients chose to share, never chat content. Not built yet: ratings and reviews, payouts, calendar sync, and checks against official registers.

## ADR-066 — Standalone Meal Planner (Phase C, 2026-10-08)

**Context:** the specification asks for a Meal Planner separate from the chat planner:

- conversational rather than a form;
- adaptive questions, then a personalised plan that can be reviewed and regenerated;
- limits from subscriptions (free 1–2 days; paid up to a week, a month, 6 months or a year);
- output with meals, portions, nutrition, ingredients, method, shopping, substitutions and goal alignment.

**Decision:**

- **Where:** `/planner`, for signed-in accounts, behind the Meal Planner feature flag. The chat planner is unchanged.
- **Intake:** one AI call per turn (`lib/planner/intake.ts`).
  - The app keeps the facts (`PlannerFacts`) and decides what is still needed, in order (`missingTopics`): goal, people and ages, allergies, a budget for budget goals, a direction for weight goals, then one open "anything else?" question.
  - The AI phrases the next question and reads the answer. Health facts (allergies, conditions, pregnancy, state, budget) are also detected by the app's own vocabularies, and the AI cannot remove a declared allergy.
  - **Blocked by code, with the app's own wording:** babies under 6 months only; weight loss for children or in pregnancy; a mentioned eating disorder.
  - Emergency signs show the urgent-care notice.
- **Lengths and limits:** 1 day, 2 days, 1 week, 1 month, 6 months or 1 year, cut by the `mealPlanner.maxDays` entitlement. Every limit is an entitlement:
  - `mealPlanner.plansPerMonth` is counted when a plan is created and refunded if generation fails;
  - `mealPlanner.adjustmentsPerWeek` (free: 1) limits rewriting a week or replacing a meal;
  - `mealPlanner.shoppingList` (free: off) adds a priced shopping list;
  - `mealPlanner.customObjectives` (free: off) allows a goal in your own words.
- **Generation** (`lib/planner/generate.ts`):
  - Plans are written one week at a time, and later weeks on request.
  - A week is written as 2-day chunks in parallel. Each chunk centres on different staples from a fixed Nigerian rotation and sees earlier weeks' meals, so days stay varied. Each chunk may take 60 seconds (`JsonRequest.timeoutMs`).
  - Every day must have breakfast, lunch and dinner, or the meals the user chose.
  - Each chunk passes the chat's deterministic checks: allergies, foods to avoid, infant and under-5 rules, pregnancy foods, and doses. A failing chunk is regenerated once with the correction, then refused.
  - The AI never gives calories or nutrient amounts.
- **Nutrition** (`lib/planner/nutrition.ts`) is calculated by the app from the food database. An ingredient counts only when it matches a database food and its weight is plausible: AI grams, or pieces times the documented serving weight, at most 400 g per person per meal. A day's figure is shown only when at least 60% of its ingredients counted, and always says how many did.
- **Shopping** (`lib/planner/shopping.ts`) totals the week's ingredients and prices them from the NBS estimates only where the unit converts:
  - by weight, by piece, or oil by millilitre;
  - processed forms (paste, flour…) are never priced as the raw food;
  - everything else is listed without a price;
  - it is labelled as estimates.
- **Review:** each day shows its meals with portions, the reason for each meal, ingredients and method, swaps and the day's goal note. Users can rewrite a week with feedback, replace one meal, write the next week, print, or delete the plan and its intake conversation.
- **Referrals:** the plan page shows the chat's referral note for sensitive situations, and up to two verified nutritionists when the directory is on (ADR-064).
- **Gemini overload:** after the primary model fails over, requests use the fallback model directly for 60 seconds (`PRIMARY_COOLDOWN_MS`). This stops every request spending its time on the overloaded model first.
- **Privacy:** intake facts and plans are kept until the user deletes them or the account. The privacy notice now describes accounts, the planner, nutritionists, payments and email.

**Consequence:**

- Limitations of the estimates:
  - Weights are AI estimates, so nutrition is approximate and partial by design.
  - Price coverage is limited to the NBS items, so rice, for example, is unpriced.
- Not built: vendor and product recommendations (Phase D), and stored plans for anonymous users.
- A plan uses about 4 AI calls per week, plus one per conversation turn, so the free Gemini tier's daily quota runs out quickly.

## ADR-067 — Vendors and Sponsored Product Recommendations (Phase D, 2026-10-08)

**Context:** the specification asks for verified food businesses to submit products, for a recommendation engine across NE's journeys, product information pages and a vendor portal. Sponsored recommendations must be clearly distinguishable from nutritional guidance.

**Decision** (consistent with ADR-064; no new product-owner questions were needed):

- **Businesses:** a vendor is an `Organization` of kind `vendor` with a `VendorProfile`, owned by one account (`Membership` role `owner`). One business per account for now.
  - Statuses: draft, submitted, changes requested, verified, rejected or suspended. `Organization.status` mirrors the review.
  - Changing the name, CAC registration or categories of a verified business sends it back to review.
- **Products:** name, category, description, benefits, recommended use, ingredients, allergens, match terms, an optional nutrition label, availability, an optional price, up to 5 places to buy, and an image (Cloudinary, public, shown only when listed).
  - Allergens are what the vendor ticks plus what the app's allergen vocabulary finds in the name and ingredients.
  - The label is shown as "from the vendor's label, not verified by Nutraboom Equals" (CLAUDE.md §13).
  - Any edit to a verified product sends it back to review.
- **Blocked by code** (`lib/vendors/product.ts`); a product cannot be submitted or approved with:
  - treatment or outcome claims (cures, treats, prevents, heals, detox, guaranteed weight loss…) or disease names;
  - breast-milk substitutes (infant formula, follow-on and growing-up milks), because Nigeria applies the International Code of Marketing of Breast-milk Substitutes;
  - a missing description, ingredients or place to buy.
- **Review** (n-equals Vendors, `vendors.verify`): a queue of businesses and of businesses with products awaiting review. Approve, request changes, reject, suspend or reinstate, for the business and for each product, with a note required for negative decisions. Nobody can review their own business. Each decision is notified to the owner and audited.
- **Listing:** shown only when the Vendors flag is on, the product and business are verified, and the business holds `vendor.listing` (free tier default off, from a vendor plan). `vendor.maxProducts` (free: 3) limits the catalogue.
- **Billing:**
  - Vendor plans are held by the organisation: checkout, return, cancellation and manual grants act on the business the account owns.
  - Paystack and Flutterwave events for a business are matched through its owner's email.
- **Recommendation engine** (`lib/vendors/recommend.ts`) is deterministic. A product is offered only:
  - when it is one of the foods the app is already suggesting (a reply's recommended foods, shopping list or meal plan; the Meal Planner's week);
  - when it is safe: no allergen of the person, no avoided food, and none of the infant, under-5 and pregnancy rules (`checkReply`);
  - when it is in stock.
  - Order: the user's state first, then online, then anywhere. At most one product per food. Two products in chat, three on a plan. Never in an emergency, and a failure never breaks chat.
- **Separation from guidance:** every card says "Sponsored · verified vendor", and every group explains that vendors pay to be listed, that it is not nutrition advice and that Equals does not sell the product. Product pages repeat this.
- **Product pages:** `/products` (search and category) and `/products/[id]`. Where-to-buy links go through `/products/[id]/go/[i]`, which counts the click and redirects only to an https link stored on a listed product (no open redirect).
- **Vendor portal** (`/vendor`): dashboard (review status, 30-day counts of recommended, opened and where-to-buy clicks per product, notifications), business profile and logo, products, and plan.
- **Analytics:** `ProductStat` holds daily counts per product only: no user, session or address.

**Consequence:**

- Not built: richer customer engagement data (deliberately none beyond counts), product ratings, stock syncing, multiple members per business, and checks against NAFDAC registration.
- Recommendations depend on vendors choosing good match terms; reviewers check them.

## ADR-068 — Hospitals and the Accessibility Agent (Phase E, 2026-10-09)

**Context:** the specification asks for a hospital directory, appointment booking and an accessibility service so that patients who are deaf, hard of hearing, blind, speech-impaired or who prefer text can reach hospital staff. Product-owner answers (2026-10-09): place search with OpenStreetMap, closed conversations kept 90 days, sign language left out for now, speech through the browser only (ADR-069).

**Decision:**

- **Hospitals:** an `Organization` of kind `hospital` with a `HospitalProfile` and `HospitalDepartment`s. Same review statuses as vendors (ADR-067), reviewed in n-equals Hospitals (`hospitals.verify`); nobody reviews a hospital they manage. Changing the name, address or registration of a verified hospital sends it back to review.
  - Submitting needs an address, state, map location, phone and one bookable department.
  - Accessibility services are a fixed vocabulary (`lib/hospitals/accessibility.ts`); sign language is not offered.
- **Staff:** members with roles owner, admin (both manage the hospital), doctor, nurse or staff, optionally limited to departments. Added by the email of an existing account; `hospital.maxStaff` (free: 5) limits them. Staff limited to departments see only those departments' appointments and conversations (and conversations with no department).
- **Location:**
  - Places are looked up with OpenStreetMap Nominatim (`lib/geo/nominatim.ts`): Nigeria only, at most one request a second across the app, a User-Agent with the privacy contact, results cached in `GeocodeCache` (misses for 7 days; outages are not cached). `NOMINATIM_URL` can point to another server.
  - Patients may instead share their device's position for one search; it is not stored.
  - Hospitals are pinned from their address or from a device at the hospital, and must be inside Nigeria.
  - Distance is haversine (`lib/geo/distance.ts`). The directory searches within a default radius (n-equals Settings, default 10 km) and offers to widen it (5–100 km, or any distance). Without a place, it filters by state.
- **Listing:** shown only when the Hospitals flag is on, the hospital is verified, and it holds `hospital.listing` (free tier default off; from a hospital plan held by the organisation, like vendor plans).
- **Booking** (`lib/hospitals/slots.ts`): slots are computed by code from each department's weekly opening times (Lagos time), slot length and capacity, with 2 hours' notice and at most 60 days ahead. The slot is rechecked inside a serializable transaction. Patients state their access needs and an optional note, and must consent to share them with the hospital. At most 3 upcoming appointments per hospital per patient. Staff mark attended, did not come, or cancel; patients cancel from their account.
- **Accessibility agent** (`lib/hospitals/agent.ts`, prompt `hospital-agent-v1`): it only routes a patient's message — category, department, whether a doctor is needed, a summary for staff, and a short reply telling the patient what happens next.
  - Emergencies are decided by code (`detectRedFlags`): the patient is told to call 112 or go to the emergency department, and every staff member is alerted.
  - The department must be one of the hospital's; a reply that mentions medicines or doses is replaced by fixed wording; with no provider or on failure the app routes by rules alone.
  - Staff are notified by role and department (doctors when a doctor is needed, nurses and staff otherwise, everyone when urgent; managers when nobody matches). A staff member can take the conversation so colleagues know it is handled.
- **Conversations:** text, with each message marked when it was spoken. Both sides poll every 5 seconds through `/api/access-conversations/[id]` (patient or hospital member only). Staff names are not shown to patients.
- **Retention:** closed conversations are deleted 90 days after closing; patients can delete theirs at any time. A daily Vercel Cron (`/api/cron/hospitals`, `CRON_SECRET`) deletes them and sends appointment reminders for the next 36 hours, once each.

**Consequence:**

- Not built: sign-language video, live calls, map tiles on our pages (links open OpenStreetMap), push notifications, and checks against hospital registers.
- Polling, not websockets: simple on serverless, at most a few seconds' delay.
- The public Nominatim server is rate-limited; heavy use needs a self-hosted or paid geocoder via `NOMINATIM_URL`.

## ADR-071 — Continue with Google (2026-10-09)

**Context:** the product owner asked for Google sign-up and log-in next to email and password (ADR-061).

**Decision:**

- OpenID Connect authorization code flow with PKCE (S256), `state` and `nonce`, done by our server (`lib/auth/google.ts`, `/api/auth/google` and `/api/auth/google/callback`). No new dependency.
- The attempt (state, verifier, nonce, where to go next) lives in a 10-minute httpOnly, SameSite=Lax cookie scoped to `/api/auth/google`. `next` is limited to same-site paths.
- The ID token comes straight from Google's token endpoint over TLS with our client secret, so we check its issuer, audience, expiry and nonce, not its signature (OpenID Connect Core 3.1.3.7). Google's tokens are not stored; `OAuthAccount` keeps only the provider and Google's stable account id (`sub`).
- **Accounts:** a known Google account signs in its user. Otherwise a verified Google email finds the existing account and links it, or creates a confirmed account with no usable password (the person can set one with "Forgot your password?"). Unverified Google emails are refused.
- **Pre-hijacking:** when Google links an existing account whose email was never confirmed, that account's password and sessions are removed, because whoever set them had not proved they own the address.
- Rate-limited with the sign-in limit; failures return to `/sign-in?error=…` with a plain message; events are logged without personal data; sign-ins are audited. The button is shown only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set, and follows Google's branding (white, four-colour G, "Continue with Google").

**Consequence:** the redirect URI `<APP_URL>/api/auth/google/callback` must be registered with Google for each environment. Only the main site offers Google; n-equals keeps password sign-in.

Email changes and account deletion stay manual (privacy notice). Validation errors are tied to their fields, and results receive focus so they are announced.

Visitors are sent to sign up with `next=/planner` and come back after; signed-in people see the shared `PlannerHome` (also on the dashboard) with an empty state, conversations to continue and saved plans. Plan pages and actions already enforce ownership on the server (ADR-066). The dashboard has a loading state that announces itself to screen readers (the planner has none, so its sign-in redirects stay real HTTP redirects).
- Sign-in, sign-up and password pages moved to the `(account)/(auth)` route group (same URLs) so the dashboard can be wide.

## ADR-076 — Hero Animation and Accessibility Baseline (2026-10-09)

## ADR-077 — Sign-Language Response Simulation (2026-10-09)

**Context:** the product owner asked for a temporary demonstration of sign-language video responses across the platform, before a real provider and credentials exist (ADR-073). The videos must be real, short, legally playable, and never presented as translations.

**Decision:**

- **Provider interface** (`lib/sign`): `SignLanguageResponseProvider.respond({ text, module, exclude })` returns `{ kind, video, notice }` or null. `DemoSignProvider` returns a random video from the collection, ignoring the text; `ProductionSignProvider` is reserved and unavailable (no endpoints are guessed). `SIGN_LANGUAGE_PROVIDER` selects `demo` (default), `production` or `off`. Provider logic runs on the server behind `POST /api/sign-language` (validated, size-limited, rate-limited, `no-store`).
- **Videos** (`lib/sign/demo-videos.ts`): 10 clips of 5–57 seconds from Wikimedia Commons under CC0 or CC BY-SA, played from Wikimedia's servers (not copied), with author, licence and source shown under each video. Nigerian Sign Language first (4), then Ghanaian (2), Tanzanian (2), American and Spanish Sign Language (1 each); the language is shown with every video, because sign languages are not interchangeable. Durations were read from the files and each was confirmed to play in a browser. Small WebM transcodes first, MPEG-4 fallback for browsers without WebM.
- **One player for every module** (`components/sign/SignLanguageResponse.tsx`): the assistant chat, the Meal Planner conversation and hospital messages (patient side). Nutritionist and vendor features have no reply conversations, so they have no sign-language response. The newest reply loads its video automatically; older replies offer "Show sign language video (demo)", so a long conversation never loads many videos. One video plays at a time.
- **Choice:** "Sign language response (demo)" is one device setting shared by all three modules (chat settings and a toggle next to each message box).
- **Always honest:** every video shows "Demo mode: This is a sample sign-language video and does not translate or represent your response.", which is also the video's accessible description. The text reply is never changed or hidden.
- **Failures:** a video that errors or does not load within 20 s is remembered for the visit (session storage), reported to the server (logged by id only, never the text) and replaced by another; when none is left the player says so and stops. Native video controls plus Replay and "Show another demo video"; videos start muted, and autoplay only when reduced motion is not requested.

**Consequence:**

- Some Nigerian Sign Language clips have a spoken voice-over; players start muted. Several clips show students of a special-needs school, uploaded with a free licence; review the collection with the Deaf community before any public demo.
- Wikimedia may refuse automated requests; browsers are served normally. If a clip is removed, the player skips it.
- Replacing the demo: implement `ProductionSignProvider`, set `SIGN_LANGUAGE_PROVIDER=production`; the player and modules stay as they are.

## ADR-078 — Sponsored Products Only at the Right Moment (2026-10-09)

**Context:** sponsored products (ADR-067) appeared under every reply that named a food. The product owner asked that they appear only when the conversation turns to buying, near its end, or when the person asks for product suggestions.

**Decision:**

- `productMoment()` (`lib/vendors/product-moment.ts`) decides in code, from the person's own words and the reply's structure. The AI cannot trigger products.
  - **asked:** the message asks for products, brands or what to buy.
  - **purchase:** buying words (buy, order — not "in order to" — shop, where can I get, who sells, delivery, how much is), or the reply carries a shopping list.
  - **closing:** a finished meal plan, or a short wrap-up ("thanks, that's all", "okay, great") after at least two replies, with no new question in it.
  - Anything else (food facts, clarifying questions, advice) shows no products.
- For "asked" and "closing" turns whose reply names no food, products can match foods discussed in the last few messages (`recentText`): a product's own match terms are looked for there, and foods in the reply still rank first.
- Unchanged: never in an emergency or a safety-sensitive reply, at most two products, the same allergy, avoided-food and child and pregnancy filters, and always labelled sponsored.

**Consequence:** fewer, better-timed product suggestions. The phrase rules are English; other reply languages still get products with shopping lists and finished plans. If needed later, the AI can be asked to flag buying intent as structured data, with code still making the decision.

## ADR-079 — Claude: Verify the Chat Request, Survive a Rejected Fallbacks Beta (2026-10-12)

**Context:** in production, a Claude key passed verification in n-equals but every chat failed in about half a second with `errorCategory: "provider"`. Verification sent a plain request; chat sends a different one (the `server-side-fallback-2026-07-01` beta with `fallbacks: "default"`, structured output with the reply schema, low effort). The logs gave no reason, because provider error bodies were never logged.

**Decision:**

- `verifyClaude` sends one reply exactly as chat does (`ClaudeProvider.generateResponse`). A key and model that pass verification therefore work in chat.
- If the API rejects the fallbacks beta (400 or 403 that mentions fallbacks or the beta header), the provider retries once without it and stops sending it from that instance. Server-side fallbacks are optional; a chat must not fail for them.
- Failed requests log `claude_request_failed` (or `claude_fallbacks_rejected`) with the model, HTTP status and the API's own error type and message, capped at 300 characters. The API message describes the request (model, parameters, schema, billing), never the conversation. No prompt or message content is logged.

- **Schema limits (found through the new log line):** structured outputs allow at most 24 optional properties per schema and limit union-typed properties too. The reply schema had 34 optional properties, so every chat failed with a 400. `claudeSchema` (Claude only) makes optional free-text and list properties without an enum required. The model writes `""` or `[]` when it has nothing, and `dropEmptyOptionals` removes those before validation. The app sees the same shape as before, and an empty list never meant anything different from a missing one. The reply schema now has 16 optional properties. A unit test keeps the chat, hospital, nutritionist and planner schemas within the limits. Gemini and OpenAI-compatible providers still get the original schemas.

**Consequence:** a misconfigured key or model is caught at verification, the beta can no longer break chat, and production failures show the exact reason in the logs.

## ADR-080 — n-equals: Platform Users and Administrators, Admin Profile, Pagination, Analytics (2026-10-13)

**Context:** n-equals listed every account in one "Users & roles" table, with roles edited inline, no deletion, and at most 25 or 100 rows per table. The overview showed three figures, the sidebar used a text placeholder for the logo, and XEELAA had its own card on the AI providers page.

**Decision:**

- **Platform users** (`/users`) lists accounts without an admin role: search, last active, suspend and **delete**. Deletion needs the new `users.delete` permission (super and platform administrators). It asks for confirmation and cascades to the person's sessions, subscriptions, meal plans, appointments and profiles (all `onDelete: Cascade` in the schema). Nobody can delete their own account. An administrator cannot be deleted until their roles are removed, and the check runs in a serialisable transaction. The audit entry keeps the account ID only.
- **Administrators** (`/admins`) lists accounts with a role. With `roles.manage`, roles are edited there, and "Add an administrator" gives a role to an existing account or creates a new one (name and a temporary password). Removing every role makes the account an ordinary platform user and ends its n-equals sessions. The last super administrator still cannot lose the role.
- **My profile** (`/profile`), for every administrator: change name, change password (other sessions end, this one continues), sign out of other sessions, see roles.
- **Pagination** on every table and list (users, administrators, nutritionists, vendors, hospitals, subscriptions, audit log, AI configurations and activity): 20 rows a page, links that keep search and filters, and an out-of-range page clamped to the last one (`n-equals/lib/pagination.ts`, `components/pagination.tsx`).
- **Logo:** the Equals logo, imported from `public/brand`, in the sidebar and on sign-in, with the cream version in dark mode.
- **XEELAA** is a provider option in "Add an API key" (no model field; "use for chat" switches it on) and a row in Saved configurations with its switch, re-check, usage and delete. The integration itself is unchanged (ADR-052).
- **Analytics** on the overview, each section by permission:
  - active AI (provider, model, last check, XEELAA state, failing keys);
  - active users (accounts with a main-site session used in 1, 7 and 30 days);
  - platform users, new and suspended;
  - chats started (stored conversations) and meal plans;
  - daily charts of sign-ups and chats over 14 days;
  - upcoming nutritionist sessions and hospital appointments, product impressions and click rate;
  - active and past-due subscriptions, and monthly recurring revenue from paid plans (yearly plans count as a twelfth);
  - review queues.

  Counts only; no names or message text. The chart uses a single validated colour token (`--chart`) and includes a table view.

**Consequence:** each kind of account is managed in its own place, deletion is possible and audited, and the overview answers "is the AI working and are people using it". Chat counts come from stored conversations, which expire, so long windows undercount.

## ADR-085 — Visual Explanations from a Reviewed Image Library (2026-10-14)

## ADR-087 — WhatsApp Through Meta's Cloud API (2026-10-14)

**Decision:**

- People can message the service on WhatsApp. Text messages run through the same `handleChat` pipeline and safety checks as the website. Replies are text, with the meal plan and shopping list written out, plus reviewed pictures as images.
- **Webhook:** `/api/whatsapp/webhook` verifies Meta's challenge (GET) and checks `X-Hub-Signature-256` with the app secret on the raw body, in constant time. It answers 200 at once and works after the response (`after()`).
- **Retries:** duplicates are skipped by message ID.
- **Consent:**
  - The service only replies, inside WhatsApp's 24-hour customer-service window; it never starts conversations or sends templates.
  - The first reply explains the service, privacy and STOP.
  - STOP and START switch messages off and on.
- **Storage (new tables `WhatsAppContact`, `WhatsAppMessage`):**
  - an HMAC of the phone number, never the number itself;
  - consent;
  - the conversation ID;
  - message IDs with delivery status (sent, delivered, read, failed), never text.
- **Limits:** the chat rate limit applies per contact.
- **Configuration:**
  - `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET` and `WHATSAPP_VERIFY_TOKEN` are required.
  - `WHATSAPP_API_VERSION` defaults to `v25.0`, available until July 2028.
  - The module is off (404) without the four required values.
- **Refactor:** `lib/http/chat-deps.ts` holds the chat dependencies shared by `/api/chat` and WhatsApp.

**Consequence:** setup and policy notes are in `docs/whatsapp.md`, and the privacy notice names WhatsApp. Business-initiated messages (reminders) would need approved templates and recorded opt-in; they are not built.
